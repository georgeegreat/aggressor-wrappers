fix(net): a redirected POST must stay a POST

Three predictors failed in ways that read as outages and were not. Two of them
have the same cause.

urllib does not follow 307 or 308 after a POST. Its redirect_request accepts
those codes for GET and HEAD only and raises otherwise, so a service that has
moved and says so in the way the specification provides for comes back as
"HTTP Error 307: Temporary Redirect". WALTZ answers exactly this. Nothing about
it is transient, so the retry layer could only turn one failure into several.

The sibling case is quieter. urllib converts a 301 or 302 after a POST into a
GET, which is settled browser behaviour and is usually right. It is wrong when
the redirect is a bare scheme upgrade -- the same host and path, http moved to
https -- because the body is dropped and the service answers whatever an empty
GET produces. PASTA returns its policy page, and the runner reported "PASTA
submission did not return a job URL: .../policy.html", which names the symptom
and hides the cause.

_MethodPreservingRedirect repeats the request, method and body intact, for 307
and 308 always, and for 301 and 302 only when nothing but the scheme changed.
Every other redirect keeps urllib's behaviour: altering 301 and 302 in general
would change how every runner handles redirects nobody has looked at, which is
a larger claim than this evidence supports. Host and Content-Length are dropped
from the carried headers, since both describe the request that was answered and
urllib recomputes them.

The opener is built once. build_opener installs the whole default handler set,
and a fresh opener per request would mean a fresh connection pool each time.

Four tests, against a local server that issues the redirects. One of them pins
the plain-urlopen behaviour being worked around, so that if urllib ever follows
307 itself the fix is not left looking like a workaround for something that no
longer happens. The scheme-upgrade predicate is tested on the cases that must
NOT match -- a changed path, a changed host, no upgrade at all -- because a
predicate that is too generous here silently re-POSTs to somewhere else.

[runners.amylodeep] gains two settings, for a failure with no network in it.
The runner's 1800-second default is a web-service figure; AmyloDeep embeds
every window with ESM2 on the CPU, so a 505-sequence batch of ~650-residue
proteins is hundreds of thousands of forward passes. It was killed mid-run and
the batch was lost entire, because sequences_per_run was unset and the whole
input went as one batch with no resume point. 7200 seconds per batch and 25
sequences to a batch: the model now loads more than once, and an interruption
costs one batch instead of all of them.

FoldAmyloid is untouched. Its log shows one sequence per request and timeouts
against the server, which is not a client defect, and raising concurrency
against a service already timing out would be the wrong answer to it.
